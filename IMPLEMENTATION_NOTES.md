# Implementation Notes — VALLI SecurePay AI

What's actually been built so far against the [MVP Blueprint](VALLI_SecurePay_AI_MVP_Blueprint.md), and the reasoning behind each decision.

## Phase 0 — Foundations

### What

- **Postgres + Redis via Docker Compose** ([infra/docker-compose.yml](infra/docker-compose.yml))
- **Full DB schema** from Blueprint Section 4 — 15 tables — as SQLAlchemy models ([backend/app/models/](backend/app/models/)) + a single Alembic migration ([backend/app/db/migrations/versions/0001_initial_schema.py](backend/app/db/migrations/versions/0001_initial_schema.py))
- **JWT auth** for human analysts — real login replacing the demo stub ([backend/app/core/security.py](backend/app/core/security.py), [backend/app/api/v1/auth.py](backend/app/api/v1/auth.py))
- **API-key auth** for integrating banks' backends — a second, independent auth path ([backend/app/models/bank_client.py](backend/app/models/bank_client.py), `get_current_bank_client` in [backend/app/core/dependencies.py](backend/app/core/dependencies.py))
- **CSV seed script** backfilling customer/merchant/device history ([backend/app/scripts/seed_from_csv.py](backend/app/scripts/seed_from_csv.py))

### Why

- **Two separate auth mechanisms, not one.** A human analyst logs into a console (email/password → short-lived JWT session). A bank's backend calling the scoring API programmatically isn't "logging in" — it needs a static, long-lived credential it stores in its own secrets manager. JWT and API-key auth solve different problems; using JWT for both would mean either sessions that never expire (defeats the point of JWT) or a bank re-authenticating on every batch job (operationally absurd).
- **Device history exists specifically to fix a named bug.** The blueprint calls out that `is_new_device` flags ~100% of traffic today because there's no persisted history to check against. `customer_devices` (with `first_seen_at`/`last_seen_at` per customer↔device pair) is that history — Phase 1's feature builder will read it instead of trusting a per-request guess.
- **`bank_clients` is a separate table from `users`**, not a role on the same table, because the two have almost nothing in common structurally: one authenticates via password hash + session, the other via a hashed static key with no session concept at all. Conflating them would mean nullable columns and conditional logic everywhere they're used.
- **API keys are hashed with SHA-256, not bcrypt.** Bcrypt's slow hashing exists to defend low-entropy, human-chosen passwords against brute force. An API key is a 256-bit random secret generated by `secrets.token_urlsafe(32)` — already too high-entropy to brute force — so a fast deterministic hash is the right tool; bcrypt would just add latency for no security benefit.

### How

- **Migration table order was fixed relative to the blueprint's own SQL.** The blueprint's raw schema has `transactions` referencing `batch_jobs` and `batch_jobs` referencing `users`, but defines both *after* `transactions` in the script — a forward-reference that doesn't execute in Postgres. The migration creates `users` → `bank_clients` → core reference tables → `model_versions`/`rules`/`decision_thresholds` → `batch_jobs` → `transactions` → `decisions` → `rule_hits` → `audit_log`, resolving every FK before it's needed.
- **Postgres runs on host port 5433, not 5432.** A native Windows Postgres service was already bound to 5432 on the dev machine, silently swallowing connections meant for the container (same symptom as a wrong password — Postgres rejected credentials because a *different* Postgres instance was answering the request). Moved the container's host mapping rather than touching the pre-existing service.
- **The CSV seed aggregates, it doesn't copy rows 1:1.** `customer_risk_score` and `merchant_risk_score` carry a small amount of per-transaction noise in the generator, so the seed script averages them per entity (`groupby(...).agg(...)`) rather than taking an arbitrary single row. `account_created_at` is derived from each customer's earliest observed transaction minus their (constant) `account_age_days`. Bulk load uses Postgres `COPY` via `psycopg2`, not row-by-row `INSERT` — the difference between seconds and hours at 1M rows.
- **A known data limitation, surfaced rather than hidden:** the generator draws `device_id` from a pool of 2M for 1M transactions largely independently of customer, so `customer_devices` came out to exactly 1,000,000 rows — almost no repeat customer↔device pairs. The mechanism is correctly built; the synthetic data doesn't yet exercise it. Flagged for whoever revisits `gen_10lakh.py`.
- **Verified live, not just written:** containers up → migration applied (`alembic upgrade head`, confirmed via `\dt`) → CSV seeded (289,245 customers / 50,000 merchants / 786,365 devices / 1,000,000 customer-device pairs) → demo analyst + demo bank client created → `POST /v1/auth/login`, `GET /v1/me`, `GET /v1/me/bank` all round-tripped end-to-end with correct 401s on bad credentials.

## Phase 1 — Model Selection Pipeline

Full results are in [ml/artifacts/model_selection_report.md](ml/artifacts/model_selection_report.md). This section is about the pipeline itself — what each stage does and why it exists.

### What

Eight numbered scripts in [ml/training/](ml/training/), run in order, each reading the previous stage's output and writing its own to `ml/artifacts/`:

| Stage | Script | Produces |
|---|---|---|
| 01 | `01_data_quality.py` | Missing values, duplicates, class balance, amount stats |
| 02 | `02_leakage_analysis.py` | Univariate AUC per feature — leakage sanity check |
| 03 | `03_prepare_data.py` | Time-based train/val/test split + engineered features |
| 04 | `04_train_models.py` | Trained LR/RF/XGBoost/LightGBM + scored predictions |
| 05 / 05b | `05_evaluate_models.py`, `05b_latency_benchmark.py` | Full metrics suite on validation |
| 06 | `06_threshold_policy.py` | Cost-optimized APPROVE/STEP-UP/MANUAL REVIEW/DECLINE bands per model |
| 07 | `07_business_value_simulation.py` | Dollar-value simulation → champion selection, `champion.json` |
| 08 | `08_final_test_evaluation.py` | One-time evaluation of the locked champion on test |

[ml/training/common.py](ml/training/common.py) holds everything shared across stages — feature spec, cost/efficacy assumptions, and every metric function — so all four models are measured identically. Nothing about a metric's definition should ever depend on which script is calling it.

### Why

- **Model selection happens in three separate passes, not one.** Stage 05 ranks models on ML metrics alone. Stage 07 re-ranks them on simulated dollar value using their own tuned policies. These *can* disagree — a model with marginally worse PR-AUC can still win on net value because it has fewer/cheaper false positives. That's the entire point of doing both: PR-AUC is a proxy, dollar value is the thing that's actually being optimized for.
- **The split is time-based, not random-stratified**, because a random split lets the model train on transactions that happen minutes after ones it's tested on. That inflates every offline metric relative to what the model faces in production, where it only ever scores the future. It also makes weekly stability checking possible — a random split scrambles time and destroys the ability to ask "does this hold up week over week."
- **Leakage analysis runs before any model does**, because a model can't tell you it's leaking — a near-perfect validation score looks identical whether it's genuine signal or a field that's only populated after the decision was made. The check (univariate AUC per feature) is deliberately dumb and cheap: if one feature alone predicts fraud almost perfectly, that's worth a human's attention before anything is trained on it.
- **PR-AUC is the headline metric, not ROC-AUC**, because at a 3% fraud rate ROC-AUC is dominated by the easy 97% of legitimate traffic and compresses real differences between models. This is a direct, explicit response to the requirement that True Positive Rate and False Positive Rate both be watched, not just one aggregate number.
- **Thresholds are swept for net dollar value on validation scores, never picked by eye or defaulted to 0.5.** The method: price each action's false-positive cost (step-up ≈ $2, manual review ≈ $15, decline ≈ $50 — labeled placeholders), sweep candidate cutoffs, take the one maximizing `fraud $ caught − cost × false positives`, subject to guardrails (max FPR per band, and a TPR-near-100% check — an over-eager threshold is a red flag, not a win, per the original brief). Two further constraints — analyst review capacity and total alert volume — can override the cost-optimum outright if it implies more daily volume than operations could actually work.
- **Test is read exactly once, at the very end.** Every decision upstream — which model, which thresholds, which policy — is made on validation only. If test informed any of those choices, the final numbers would be an overestimate of what the model does on genuinely unseen data, which defeats the purpose of holding out a test set at all.
- **Business-cost and prevention-efficacy numbers are explicit, labeled assumptions, not invented facts.** Nobody supplied real figures for what a wrongful decline costs in churn, or what fraction of step-up-triggered fraud actually gets deterred. Rather than skip the analysis or quietly bury a guess, every such number lives in one place (`common.py`'s `ACTION_FP_COST` / `ACTION_PREVENTION_EFFICACY`) and is called out in the report's Assumptions table — swap the constant, rerun stages 06–08, get corrected numbers, without touching the method.

### How

- **`common.py` is the single source of truth** for the feature list, the target column, and every metric function (`pr_auc`, `recall_at_fpr`, `precision_at_k`, `dollar_capture`, `calibration_report`, `fraud_type_recall`, `weekly_stability`, `latency_benchmark`). Each numbered script imports from it rather than redefining anything — the four-model comparison is only meaningful if every model is measured with the exact same code.
- **Feature engineering adds four fields the raw dataset doesn't have**: `amount_to_avg_ratio` (this transaction vs. that customer's own average — turned out to be the single strongest univariate signal, AUC 0.80), `is_cross_border`, `is_ip_merchant_country_mismatch`, and cleaned nulls on a few numeric fields. Everything else is used as generated.
- **All four models share one `ColumnTransformer`** (`StandardScaler` on numerics, passthrough on booleans, `OneHotEncoder` on the five categoricals) fit once on train and reused for val/test — guarantees identical feature encoding across models, and the fitted preprocessor is persisted (`preprocessor.pkl`) so it can be reused at serving time in Phase 1's actual scoring API.
- **Threshold sweeping is a straightforward grid search**, not an analytic solution: candidate cutoffs are the 500 quantiles of the validation score distribution, and for each one the script computes TPR/FPR/dollar value caught/net value, then picks the net-value-maximizing candidate inside the guardrail-feasible set (falling back to the strictest-feasible candidate if guardrails and cost-optimum can't both be satisfied).
- **The capacity/alert-volume constraints are applied as a second pass**, not baked into the sweep itself: compute the cost-optimal threshold first, check whether its implied daily volume exceeds capacity, and if so binary-search for the score cutoff that hits the capacity limit exactly, then take whichever threshold is stricter. This is what actually fired for the step-up band (cost-optimum implied 526/day; alert-volume cap forced it down to ~356/day).
- **Stage 08 imports Stage 07's `simulate()` function directly** (via `importlib.import_module` — the numeric filename prefix makes a normal `import` statement invalid, but `import_module` doesn't care) rather than reimplementing the business-value math a second time, so the final test-set dollar figures are computed by literally the same code that ranked the models on validation.
- **Verified by actually running all eight stages against the full 1,000,000-row dataset**, not spot-checked: 700K/150K/150K time-based split, ~440s to train Random Forest, ~65s for XGBoost, ~21s for LightGBM, full metrics suite computed on all four, thresholds swept, business value simulated, champion locked to `champion.json`, and a genuine one-time test evaluation producing the numbers in the final report.

## Phase 1.5 — The scoring API

### What

- **`POST /v1/transactions/score`**, `GET /v1/transactions/{id}`, `GET /v1/transactions/{id}/technical-detail` ([backend/app/api/v1/transactions.py](backend/app/api/v1/transactions.py))
- **Decision engine**: [feature_builder.py](backend/app/decision_engine/feature_builder.py) (resolves history, builds the feature row), [model_loader.py](backend/app/decision_engine/model_loader.py) (loads + caches the packaged champion), [rules_engine.py](backend/app/decision_engine/rules_engine.py) (6 deterministic rules), [band_resolver.py](backend/app/decision_engine/band_resolver.py) (score + rules → band), [explainability.py](backend/app/decision_engine/explainability.py) (SHAP → plain-English reasons)
- **`ml/training/09_package_model.py`** bundles the champion model, its preprocessor, feature order, and locked thresholds into one artifact so the backend can never accidentally load a model against the wrong preprocessor or stale thresholds.
- **`backend/app/scripts/seed_model_and_rules.py`** seeds `model_versions`, `rules`, and `decision_thresholds` from that locked artifact.

### Why

- **Only three fields are ever server-resolved and override client input**: `is_new_device`, `customer_risk_score`, `merchant_risk_score` — exactly what the blueprint's Section 5.2 contract specifies, and exactly what fixes the calibration bug. Everything else (velocity counters, session duration, device age) is accepted from the request per that same contract, rather than building a full server-side behavioral-history subsystem this pass didn't need.
- **The SHAP explainer is built once and cached alongside the model**, not per-request. First cut of this shipped without that cache and measured **3.3 seconds** per score — 30x over the P50<100ms budget. Building a `TreeExplainer` means parsing the model's tree structure; doing that on every request was the entire latency problem. Caching it dropped steady-state latency to **37ms**.
- **Rule severity can override the model's band, not just annotate it**: a `critical` rule forces Decline outright (mechanism exists now, unused until a sanctioned-country data source is wired in); a `high` rule bumps a Monitor verdict to Step-up. The model doesn't get the only vote.
- **Idempotency is enforced at the transaction level**, not the decision level: resubmitting a `transaction_id` that already has a persisted `Transaction` row returns that original decision untouched (FR4) instead of silently re-scoring — this is what a real payment retry or a bank's at-least-once delivery would hit constantly.

### How

- **Feature building resolves customer/merchant/device rows, bootstrapping them if unseen** (a brand-new `customer_id` gets a `customers` row created from the request's own fields, with a neutral default risk score) rather than 404ing — matches the blueprint's framing of history as something that accumulates from live traffic, not a fixed pre-populated set.
- **`is_new_device` is computed from `customer_devices`, not `devices`** — a device can have long global history (seeded from the 10-lakh dataset) while still being new *to this customer*. Both facts are legitimately true at once, but the first pass's template wording let them read as contradictory side by side ("hasn't been seen with this customer" + "has an established history"); fixed below.
- **Decision bands live in `decision_thresholds`, read at request time**, not hardcoded (FR5) — retuning a cutoff is a DB update, not a deploy.
- **Verified end-to-end against the running stack**: seeded model/rules/thresholds, scored a deliberately extreme transaction (cross-border, IP mismatch, new device, 2x+ baseline amount, new payee) and got a correct `decline` at risk score 99.99 with all 5 expected rules firing; scored a normal transaction and got `monitor`; resubmitted the same `transaction_id` twice and got the identical persisted decision back (not a re-score); confirmed `X-API-Key` (bank) and JWT (analyst) both reach the same endpoint with correct attribution (`source=bank_api` vs `single`, `actor_type` in the audit log); confirmed 404 on an unscored transaction; checked `transactions`/`decisions`/`rule_hits`/`audit_log`/`customer_devices` rows directly in Postgres after each call.

### What's deliberately not built yet

Batch scoring (`POST /v1/transactions/batch`), the Report and Overview endpoints, and the frontend are still ahead — this phase produced a working, verified single-transaction scoring path end-to-end (feature resolution → model → explainability → rules → band → persistence), not the full console.

## Phase 1.6 — Explainability, policy versioning, and latency observability

Five fixes/additions after a closer read of the running system, in a new migration ([0002_policy_version_and_latency.py](backend/app/db/migrations/versions/0002_policy_version_and_latency.py) — a new migration, not an edit to `0001`, since `0001` had already been applied against a database with real seeded/scored data).

### What

- **Fixed a genuine explanation contradiction**: `is_new_device` and `device_age_days` could both land in the top factors and read as opposing claims — "this device hasn't been seen with this customer" next to "this device has an established history." Rewrote both templates in [explainability.py](backend/app/decision_engine/explainability.py) to be explicit about scope: one is about *this customer's* history with the device, the other is about the *device's* history overall. Same underlying facts, no longer reads as contradictory.
- **`policy_version`**: a new column on `decision_thresholds` (shared by all 4 band rows whenever they're re-seeded as a set) and `decisions` (captured at scoring time), returned in the API response.
- **`risk_score` is documented as a risk score, not a probability** — in the Pydantic field description (surfaces in the OpenAPI/Swagger docs), the `Decision.risk_score` model comment, and here.
- **Structured explainability**: `contributing_factors_detail` — a list of `{feature, category, value, shap_value, direction, explanation}` objects — alongside the existing flat `contributing_factors: list[str]`, in both the score response and `/technical-detail`.
- **Split latency**: `inference_time_ms` (preprocessing + `model.predict_proba` only) and `explainability_time_ms` (SHAP only), alongside the existing total `processing_time_ms`.

### Why

- **The contradiction was a real analyst-trust problem, not a cosmetic one.** An analyst reading two apparently-opposing bullet points in the same explanation has no way to know both are true and compatible — they'll assume one is a bug and stop trusting the explanations generally. Fixing the wording so the two facts read as complementary (customer-specific vs. device-global) fixes the actual problem; merging/hiding one of the two factors would have thrown away real signal instead.
- **`policy_version` exists because thresholds and models version independently.** `model_version_id` already tracks which model scored a transaction; without a separate `policy_version`, there was no way to know which *cutoffs* were in effect if `decision_thresholds` gets retuned later (FR5 explicitly allows retuning without a redeploy) — a compliance/audit gap for a system whose whole pitch is "every decision, replayable."
- **The probability-vs-risk-score distinction is documented in the API contract itself, not just a conversation.** A field description that only exists in chat history is not discoverable by whoever builds the frontend or the next engineer who joins — it needs to live where `/docs` (Swagger UI) and the ORM model both surface it, so "don't render this as a percentage" survives past this conversation.
- **Structured factors exist because string-parsing an explanation to build a UI (icons, sort by magnitude, color by direction) is exactly the kind of fragile coupling a real frontend shouldn't have to do.** The flat string list stays for anything that just wants to display text as-is.
- **Split latency exists because the earlier 3.3s SHAP-caching bug was invisible in a single blended `processing_time_ms`.** With inference and explainability broken out, a future regression in either one is immediately localized instead of requiring a profiler to find it again.

### How

- **`rules` couldn't be safely wiped and recreated once real decisions existed.** The seed script's original delete-all-then-reinsert pattern hit a live FK violation the moment it ran against a database with actual scored transactions (`rule_hits` referencing the old rows) — deliberately no cascade delete, since `rule_hits` is audit trail (NFR3), not disposable state. Fixed by upserting `rules` by `rule_code` instead of delete+recreate; `decision_thresholds` has no dependents, so it's still safely wiped and reseeded each run.
- **`policy_version` is a timestamp tag** (`policy-{utc timestamp}`) generated once per seed run and stamped onto all 4 band rows together, so a single `Decision.policy_version` value unambiguously identifies the whole matched set of cutoffs that produced it — not a full historical snapshot table, which would have been a bigger schema change than this fix warranted.
- **`contributing_factors` is now persisted as structured dicts** (`dataclasses.asdict` on the same `ContributingFactor` objects used to build the response), not flat strings — no new column needed, since the field was already `JSONB`. The flat string list and the structured list are both derived from this one stored representation, so they can't drift apart.
- **Latency is measured with two nested `time.perf_counter()` windows** inside the existing outer timer, not three independent clocks — `inference_time_ms` wraps `preprocessor.transform` + `predict_proba`, `explainability_time_ms` wraps the `explain()` call, and `processing_time_ms` is still the full request as before.
- **Verified against the live stack again**: applied migration `0002`, reseeded (confirmed the upsert path works against existing `rule_hits`), scored a fresh transaction with the exact new-device/old-device scenario that originally exposed the contradiction — factors now read as "this specific device has never been linked to this customer before" + "this device has a long history overall, though not necessarily with this specific customer," which is no longer self-contradictory. Confirmed steady-state latency breakdown (62ms total = 24ms inference + 14ms explainability + ~24ms everything else) on a second call, confirmed `policy_version` and `contributing_factors_detail` populate correctly on both the fresh-score and idempotent-replay paths, and confirmed `/technical-detail` returns the same structured factors.

## Phase 2 — Batch scoring

### What

- **`POST /v1/transactions/batch`** (CSV upload), **`GET /v1/transactions/batch/{job_id}`** (status/progress), **`GET /v1/transactions/batch/{job_id}/download`** (scored CSV), **`GET /v1/transactions/batch/template`** ([backend/app/api/v1/batch.py](backend/app/api/v1/batch.py))
- **RQ (Redis Queue)** background worker ([backend/app/workers/](backend/app/workers/)) — upload returns immediately; a separate `python -m app.workers.run_worker` process does the actual scoring
- **Vectorized batch scoring** ([batch_scoring_task.py](backend/app/workers/batch_scoring_task.py)) — bulk entity resolution (one `IN`-query per entity type per chunk, not one query per row), one `predict_proba`/SHAP call per chunk of 5,000 rows, bulk inserts — reusing the exact same rule definitions, band-resolution logic, and explanation templates as the single-transaction path
- **Row-level quarantine** (NFR7): malformed rows (bad amount, unparseable `transaction_time`, missing required fields) are pulled out before scoring and written to a companion `{job_id}_quarantine.csv` with a reason per row, instead of being silently dropped or failing the whole batch

### Why

- **Batch reuses the single-transaction path's logic, not a reimplementation of it.** `_vectorized_rules`, `_vectorized_bands`, and `_batch_explain` mirror `rules_engine.py`/`band_resolver.py`/`explainability.py` line-for-line in intent — same rule codes, same severity-bump behavior, same `explainability._structure()` call for humanizing SHAP values. Verified directly: the same customer/device pair (`CUS-048312`/`DEV-0582474`) scored via batch and via `/score` earlier both produced **risk_score=5.57, step_up_auth, HIGH_RISK_CUSTOMER-only** — identical to the decimal place. Two independently-coded paths that happen to agree would be luck; one path's logic genuinely reused by the other is why they can't silently diverge.
- **Column presence is validated before any row is touched** (NFR7's explicit requirement) — a CSV missing required columns gets rejected at upload with a 422 and the exact missing-column list, before a batch_jobs row even exists.
- **Quarantine, not silent drop, not whole-batch failure.** A single malformed row (negative amount, blank timestamp) in an otherwise-valid 10,000-row file would be a bad reason to fail the whole upload; silently skipping it would be worse, since nobody would know a row didn't get scored. The quarantine file makes the gap visible and actionable.
- **RQ over Celery**: the blueprint names either as acceptable ("Celery/RQ"); RQ was picked because it needs nothing beyond the Redis instance already running for the feature/history cache, whereas Celery wants its own broker configuration and result backend setup for comparatively little benefit at this scale.

### How

- **Two genuine Windows incompatibilities in RQ's default worker, both hit by actually running it, not found by reading docs:**
  1. RQ's default `Worker` forks a child process per job (`os.fork()`) for isolation — `os.fork` doesn't exist on Windows at all. Fixed by using `SimpleWorker`, RQ's documented in-process fallback (trade-off: a crashing job takes the whole worker down with it, no fork boundary — matters more here than on Linux).
  2. RQ's job-timeout enforcement uses `signal.SIGALRM` by default — also POSIX-only. Fixed by overriding `death_penalty_class` to `TimerDeathPenalty`, RQ's thread-based, signal-free alternative.

  Both failures were silent-looking at first (worker process just exited) and only diagnosable by reading the actual traceback in the worker's log — a reminder that "it imported fine" and "it runs on the target OS" are different claims.
- **`device_age_days`/`account_age_days` resolve from actual history when the CSV omits them**, not a hardcoded default — a batch upload that leaves these optional columns blank gets the same server-side resolution (`(transaction_time - first_seen_at).days` / `(transaction_time - account_created_at).days`) the single-transaction path already does. Caught this gap by re-reading the code before testing, not after: the first draft defaulted omitted values to 0 for every row, which would have made every batch-scored transaction with blank optional columns look like a brand-new account/device regardless of actual history.
- **Bulk entity resolution processes a whole chunk with a handful of queries, not N queries.** For each chunk: one `customers WHERE customer_id IN (...)` query, bulk-insert any unseen customers, repeat for merchants/devices/customer_devices pairs — the same pattern as the Phase 0 CSV seed script, applied here per-chunk instead of once for the whole file.
- **`batch_jobs.submitted_by` requires a `users.id`, so batch upload is JWT/analyst-only, not available via bank API key** — a real schema constraint (the FK has nowhere to point for a `bank_clients` row), not an oversight. Flagged rather than silently worked around; extending batch to bank callers would need a nullable `submitted_by` + a `submitted_by_bank_id` column, mirroring the same pattern already used for `transactions.submitted_by_bank_id` in Phase 0.
- **A known gap, surfaced rather than hidden**: if the worker process crashes *before* a job starts running (verified by actually killing it mid-test), RQ marks the job abandoned/failed in Redis, but the corresponding `batch_jobs` row stays stuck at `status=queued` forever — there's no reconciler that notices a job Redis gave up on and marks it failed in Postgres too. Fine for a single-worker MVP demo where a stuck job is visibly obvious; a real deployment needs a periodic sweep for stale `queued`/`running` jobs past some age.
- **Verified end-to-end against the live stack**, not just unit-level: uploaded an 8-row CSV covering a normal transaction, a new-device transaction, the same extreme-risk case proven earlier, a known high-risk customer (cross-checked against its earlier single-transaction score), a bootstrap case with a blank `average_transaction_amount`, and two deliberately malformed rows (negative amount, blank timestamp). Result: 6/8 scored correctly (matching expected bands), 2/8 correctly quarantined with accurate reasons, `batch_jobs.status` and `decision_distribution` correct, all 6 `transactions` rows correctly tagged `source=batch` and linked via `batch_job_id`, and the bootstrap customer/merchant correctly created with the amount-based fallback average. Also confirmed the CSV-template endpoint and the missing-required-columns rejection path (422, before any row touched).

## Phase 3 — Report, Overview, and admin config

### What

- **`GET /v1/transactions`** (filtered/paginated list) and **`GET /v1/transactions/export`** (same filters, CSV) — backs the Report screen ([backend/app/services/report_service.py](backend/app/services/report_service.py), [backend/app/api/v1/report.py](backend/app/api/v1/report.py))
- **`GET /v1/overview/summary`**, **`/decision-distribution`**, **`/risk-trend`**, **`/top-rules`** — backs the Overview dashboard ([backend/app/services/overview_service.py](backend/app/services/overview_service.py), [backend/app/api/v1/overview.py](backend/app/api/v1/overview.py))
- **`GET/PATCH /v1/rules`** and **`GET/PATCH /v1/decision-thresholds`** — admin-only config endpoints (FR5), gated by the existing `require_admin` dependency ([backend/app/api/v1/admin.py](backend/app/api/v1/admin.py))
- The `mv_overview_daily` materialized view (present in the schema since Phase 0, unused until now) backs `risk-trend`, refreshed on-demand at request time

### Why

- **List and export share one query-builder** (`report_service._base_query`), not two separately-maintained filter implementations — the classic bug here is export silently applying different logic than what the analyst was just looking at on screen. Both now provably see the same filtered set because they're the same query object with a different terminal operation (`.all()` vs paginated `.offset().limit()`).
- **`risk_level` is a separate concept from `decision_band`, computed independently.** `decision_band` is action-oriented and can be overridden by rule severity (a `high`-severity rule bumps `monitor` to `step_up_auth` even at a low raw score); `risk_level` is a pure score banding (low/medium/high/critical at the 25/50/75 cutoffs) with no rule involvement. Conflating them would have made the Report screen's two filters redundant instead of complementary, and would have hidden the rule-bump behavior from anyone filtering by risk level alone.
- **The admin endpoints exist specifically to make FR5 true, not just claimed.** Before this, "thresholds are configurable without a deploy" was only true via rerunning a seed script — not meaningfully different from a deploy. `PATCH /v1/rules/{code}` and `PATCH /v1/decision-thresholds/{band}` write directly to the tables `band_resolver.py`/`rules_engine.py` already query fresh on every request, so retuning takes effect on the very next transaction scored, no cache to invalidate and no restart needed. Verified directly, not assumed: disabled `NEW_DEVICE` via `PATCH`, scored a transaction with a genuinely brand-new device, and got `rule_hits: []` — confirmed the rule engine picked up the change immediately.
- **Admin endpoints are unprefixed (`/v1/rules`, not `/v1/admin/rules`)**, matching the blueprint's Section 5.6 paths exactly — access control comes entirely from `require_admin`, not from the URL shape.

### How

- **`risk_level` is a SQL `CASE` expression** (`RISK_LEVEL_CASE` in `report_service.py`), not computed in Python after fetching — it needs to work as both a `SELECT` column and a `WHERE` filter predicate (`risk_level=high` as a query param), and building it once as a reusable SQLAlchemy expression is what makes that possible without duplicating the banding logic.
- **The materialized view refreshes synchronously inside the `risk-trend` request handler**, not on a schedule — a deliberate MVP simplification, called out directly in the code comment as something a real deployment should move to a scheduled worker task (the blueprint's own "nightly + on-demand refresh" language allows this, but at real data volumes a synchronous refresh per request would erase the view's whole performance point).
- **Threshold `PATCH` validates the edited band's own `min_score < max_score`, but does not enforce contiguity across the other 3 bands** — raising `step_up_auth`'s floor without also raising `monitor`'s ceiling can open a gap or overlap between them. Documented as the admin's responsibility in both the code comment and this note, rather than silently allowing an inconsistent policy to look validated. A stricter version would accept all 4 cutoffs atomically in one request instead of the blueprint's literal per-band `PATCH` interface.
- **Verified against the live stack with the real ~65 transactions already in Postgres from earlier testing**, not synthetic fixtures: confirmed `decision-distribution` sums to `summary.transactions_analyzed` (16+30+1+18=65) and `decline_hold_rate` matches by hand ((30+1)/65); confirmed `q=CUS-048312` correctly finds that customer's transactions across both single and batch scoring; confirmed export CSV content matches the equivalent filtered list; confirmed RBAC actually blocks a non-admin (403 for the analyst user against `/v1/rules`) and actually allows a real admin user created for the test; confirmed the disable-a-rule-and-rescore live-effect test above; confirmed 422 on an inverted threshold range and 404 on an unknown rule code.

### Why

- **The frontend was 100% mock-data-driven on arrival, despite a real, fully-verified backend already existing.** Every screen rendered fabricated numbers computed client-side rather than calling the API at all — the single biggest gap between "the backend works" and "the product works," and the reason this phase was a rewrite of the data/auth/state layer rather than a styling pass.
- **Customer/merchant fields are free text with suggestions, not a locked `<select>`.** The backend doesn't require these IDs to come from a fixed list — `feature_builder.py`'s bootstrap path (Phase 1.5) explicitly creates a new customer/merchant/device row from the request if the ID hasn't been seen before. A dropdown would have silently reintroduced a constraint the API was deliberately built not to have.
- **`is_new_device`/`customer_risk_score`/`merchant_risk_score` are opt-in overrides, not always-sent fields.** The first draft of the form sent all three unconditionally on every submit, which silently defeated the server-side history resolution that's the entire point of Phase 0's `customer_devices` table and Phase 1.5's bootstrap logic — every UI-driven score would have looked like a brand-new device/customer regardless of actual history. Fixed with explicit toggles, off by default, so the server's real resolution wins unless a demo/test deliberately overrides it.

### How

- **`sampleData.js`'s customer/merchant suggestions use real seeded IDs** (`CUS-000004`, `MER-038002`, etc., queried directly from Postgres), not the placeholder IDs (`cust_501`, `merchant_112`) shipped in the downloaded template — those didn't exist in the seeded DB, so every UI-driven score would have bootstrapped a fresh no-history record instead of exercising real accumulated history.
- **`CURRENCIES`/`COUNTRIES`/`CHANNELS`/`MERCHANT_CATEGORIES` were checked against `gen_10lakh.py`'s actual generated vocabulary and matched exactly already** — no fix needed there, confirmed rather than assumed.
- **Verified live with Playwright** (`channel: "msedge"`, since the bundled Playwright Chromium had a version mismatch on this machine and `chromium-cli` wasn't available on Windows): logged in as the real analyst, confirmed Overview's real stats/charts load, submitted a single transaction and got a real risk score/decision/explanation, uploaded a batch CSV through the actual file-drop UI and downloaded real results, browsed Report and opened transaction detail. Distinguished real bugs from React StrictMode dev-only artifacts along the way (a double-effect-invocation zeroing Overview counters, an animation-timing "0.0" flash on the risk gauge, connection contention from doubled dev-mode requests presenting as a spurious timeout) — none of those reproduce outside `StrictMode`, so none were "fixed" in a way that would have actually been a workaround for a non-bug.
- **Found and fixed a duplicate-`transaction_id` crash in batch upload**: the batch worker had no idempotency check, unlike the single-transaction path, so re-uploading a file containing an already-scored `transaction_id` raised an unhandled `psycopg2.errors.UniqueViolation`. Fixed in [batch_scoring_task.py](backend/app/workers/batch_scoring_task.py) by splitting incoming rows into in-file duplicates (quarantined), already-scored rows (looked up and returned unchanged — the same FR4 idempotency guarantee the single-transaction path already has), and genuinely new rows (scored normally) — reproduced the user's exact reported scenario and confirmed the fix.

## Phase 5 — Full-stack audit and hardening

A structured audit across five categories (Data, Decisioning, Explainability, State, Error handling), each checked against the live running stack rather than by code-reading alone.

### What

- **`rule_hits` enriched from `list[str]` to structured `{rule_code, severity, description}` objects**, sourced live from the `rules` table on every response (both the fresh-score and idempotent-replay paths).
- **New `band_source`/`override_rule` fields** on `ScoreTransactionResponse`, backed by new `decisions.band_source`/`override_rule_code` columns ([migration 0003](backend/app/db/migrations/versions/0003_band_source_and_rule_metadata.py)), populated by both the single-transaction and vectorized batch scoring paths.
- **Fixed an empty/malformed-CSV crash**: uploading an empty file, or one with broken quoting, raised an uncaught `pandas.errors.EmptyDataError`/`ParserError` and returned a raw 500. Both are now caught in `batch_service.create_batch_job` and surfaced as a clean 422.
- **Batch CSV template now includes a realistic example row** (real seeded IDs, correctly formatted ISO-8601 UTC timestamp), not just a bare header.

### Why

- **The frontend had no way to answer "does it correctly show rule overrides?" because the backend never recorded the answer.** `band_resolver.py` has always been able to force/bump a band via a rule (Phase 1.5/1.6), but `ScoreTransactionResponse` only ever exposed the final `decision_band` — a caller genuinely could not distinguish "the model scored it this way" from "a rule overrode the model" from the API alone. This is the same category of gap as `policy_version` in Phase 1.6: an audit-relevant fact that existed in the engine's internal state but never made it into the persisted record or the response contract.
- **`band_source`/`override_rule_code` are persisted at scoring time, not recomputed on replay.** `decision_thresholds` rows are mutable via `PATCH /v1/decision-thresholds` (Phase 3), so re-deriving "was this an override" from *current* threshold rows during an idempotent replay of an old decision could disagree with what genuinely happened at scoring time. Storing the fact once, at the moment it's true, is what keeps replayed decisions honest.
- **`RULE_SEVERITY` had been hardcoded on the frontend** (a static mirror of the rules table, added because the API response only ever carried rule *codes*) — it would have silently gone stale the instant an admin changed a rule's severity via the already-live `PATCH /v1/rules/{code}` endpoint, since nothing re-fetched it. Enriching the response is the same fix pattern as `policy_version`: move the fact into the API contract instead of duplicating it client-side.
- **An empty or malformed CSV is ordinary user error** (an empty file exported by mistake, a spreadsheet tool that mangled quoting), not a server fault — it should read the same as the existing "missing required columns" case (422, a clear message), not surface as an unhandled exception.

### How

- **`RuleHit.rule` (the ORM `Rule` object) was already being carried through `rules_engine.evaluate_rules`** — extending the response only required reading `.severity`/`.description` off an object already in hand, not a new query, for the fresh-score path. The idempotent-replay path (`_response_from_persisted`) needed one extra column in its existing `Rule`⋈`RuleHit` join.
- **The vectorized batch path computes `band_source`/`override_rule_code` per-row with pandas boolean masks** (`_vectorized_bands` in `batch_scoring_task.py`), mirroring `band_resolver.py`'s critical-forces-decline / high-bumps-monitor logic exactly, rather than falling back to a per-row Python loop that would have undone the whole point of vectorizing this path in Phase 2.
- **`pd.errors.EmptyDataError` and `pd.errors.ParserError` are caught in `batch_service.create_batch_job` and re-raised as the existing `CsvSchemaError`**, so they flow through the endpoint's existing 422 handler rather than needing a second exception path.
- **Verified against the live stack, category by category**: confirmed all categorical values (currency/country/category/channel) already matched `gen_10lakh.py` exactly; confirmed a low-model-score transaction (7.54) for a flagged-high-risk customer correctly returned `decision_band: step_up_auth`, `band_source: rule_override`, `override_rule: HIGH_RISK_CUSTOMER` — via the single-score API, the batch CSV output, `GET /v1/transactions/{id}` (used by Report), and the rendered UI (screenshotted); confirmed `localStorage` holds only the auth token, auth user, and theme preference, nothing transaction-related; live-tested 401/422/404/403/409/duplicate-resubmission/malformed-CSV/empty-CSV/huge-CSV(20,000 rows)/unknown-customer-merchant-device against the running backend, finding and fixing the two bugs above along the way; confirmed the client's 15s request timeout produces a clean user-facing error rather than an unhandled rejection.
- **A leftover from the huge-CSV test wasn't actually cleaned up the first time**: the 20,000 synthetic `TXN-HUGE*` rows it wrote to Postgres were left behind after the on-disk CSV files were deleted, inflating every Report/Overview count until a follow-up pass deleted the `transactions`/`decisions`/`rule_hits`/`audit_log`/`batch_jobs` rows and the fabricated `DEV-HUGE001` device/history row it created. A reminder that "deleted the files" and "cleaned up the test" aren't the same claim when the thing under test persists to a database.
- **A second hardcoded-duplication gap found on a follow-up pass**: `risk_level` banding (low/medium/high/critical at 25/50/75) was computed independently in two places — a SQL `case()` in `report_service.py` and a JS function in the frontend — with no shared source, so retuning one without the other would silently desync them. Fixed by moving the cutoffs into [decision_engine/risk_level.py](backend/app/decision_engine/risk_level.py) (`RISK_LEVEL_CUTOFFS` + `risk_level_from_score()`), having `report_service.py`'s SQL `case()` build itself from that same tuple instead of repeating the literals, and adding `risk_level` to `ScoreTransactionResponse` (both the fresh-score and idempotent-replay paths) so the frontend consumes it instead of recomputing it — the same fix pattern already applied to `band_source` and rule severity. `ResultPanel.jsx`'s `RiskGauge` now reads `response.risk_level` directly; the frontend's `riskLevelFromScore()` was deleted. Verified live: a fresh score (30.06) and its replay via `GET /v1/transactions/{id}` both return `risk_level: "medium"`, and the Report detail panel renders it with zero console errors.
